# Performance

This page records what was measured, how, and what changed. The numbers come from `scripts/measure.mjs`, so anyone can
reproduce them.

## How it is measured

`npm run measure` loads a page in headless Chrome on a throttled "phone" and reports the median of several first
visits (cache disabled):

- viewport 412 × 823 at 2.6× pixel density, CPU slowed 4×, 1.6 Mbit/s with 150 ms latency (Lighthouse's slow-4G profile)
- **FCP / LCP**: first and largest contentful paint
- **CLS**: cumulative layout shift
- **main thread**: total time the browser spent on tasks while loading
- **KB over wire**: bytes transferred, after compression

When given two servers it loads them alternately, so a slow moment on the machine affects both equally. All figures
below are medians of five runs against a local server, comparing the code before this work
(commit `eb0cd79`) with the current code.

```bash
git worktree add ../drink-it-before eb0cd79 && (cd ../drink-it-before && PORT=3001 node server.js &)
npm run build && PORT=3000 npm start &
npm run measure -- http://localhost:3001 http://localhost:3000 /products/coca-cola-original-250ml-can
```

## What made the difference

**Less to download**

- Pack photos shown as 40 px swatches and cart thumbnails were the 900 px originals (about 90 KB each). Small copies
  (192 px, about 7 KB) are generated by `scripts/render/derive.mjs`. A collection page no longer loads about 5 MB of them.
- Hero, banner and blog images are offered at several widths through `srcset`; phones are kept on the 846 px hero.
- The alternate-angle photo of a product card is fetched when someone points at the card, not for every card.
- The second hero slide and the hero cans (hidden on phones) wait until the page has loaded.
- Text is served with Brotli, JavaScript is bundled and minified (about 40 KB for a typical page), and the stylesheet is
  minified into one file of about 17 KB.

**Less waiting**

- The banner image and heading, the product photo, the title and the meta tags are rendered by the server, so the
  largest contentful element is in the first HTML instead of appearing after scripts have run.
- The product page keeps the server-rendered photo in place when its script runs; replacing it with an identical new
  element made the browser count the page as painted a second time, about two seconds later.
- The catalogue and session requests are announced with `<link rel=preload>`, and the entry script's chunks with
  `modulepreload`, so they start while the HTML is still being parsed.
- The small pre-paint script is inlined (and allowed by hash in the Content-Security-Policy) instead of being a
  render-blocking request.

**Less jumping around**

- The call-to-action banner is part of the HTML instead of being injected, containers that scripts fill in reserve their
  space, and the footer stays invisible until the page is ready (with a CSS fallback if the script never finishes).

**Caching**

- Build output and every image and font carry a content hash in their URL and are cached for a year (`immutable`);
  changing a file changes its URL.
- HTML is revalidated by browsers and may be kept for five minutes by a CDN; `/api/catalogue` is cached for 30 s in
  browsers and 60 s in shared caches; per-visitor API responses are never cached.

## Things deliberately left alone

- `content-visibility: auto` on the home page sections would cut layout work, but it applies paint containment, which
  would clip the decorative torn edges and wave dividers that stick out of those sections.
- The body font (DM Sans, 62 KB) is a variable font with two axes. Pinning the axes would shrink it, but needs a font
  tool outside this project's dependencies, and the saving is a few hundred milliseconds on a slow connection at most.
